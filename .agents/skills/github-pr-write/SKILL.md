# GitHub PR 작성

## 역할

현재 브랜치의 실제 변경사항을 기준으로 GitHub Pull Request 제목과 본문 초안을 작성한다.

PR 생성, push, commit, merge, rebase는 하지 않는다.

## 기본 규칙

- 실제 변경 파일과 diff에 근거해서만 작성한다.
- 구현되지 않은 내용, 향후 계획, 추측은 포함하지 않는다.
- 확인하지 않은 테스트나 수동 검증을 완료로 표시하지 않는다.
- 사용자가 PR 생성을 요청해도 제목과 본문 초안만 제공한다.
- 이슈 번호가 확인되면 PR 본문에 GitHub closing keyword를 포함한다.
- 이슈 번호가 확인되지 않으면 임의로 만들지 않고 확인 필요로 표시한다.

## 확인 절차

먼저 변경 범위를 확인한다.

git branch --show-current
git status --short
git diff --stat
git diff --name-only

base 브랜치가 필요하면 별도 지시가 없는 한 origin/develop, origin/main, origin/master 순서로 확인한다.

전체 diff는 한 번에 읽지 않고 필요한 파일만 좁혀서 확인한다.

git diff <base>...HEAD -- <file>

문서는 변경사항과 직접 관련된 경우에만 필요한 파일만 읽는다.

이슈 번호는 사용자 요청, 브랜치명, 커밋 메시지에서 확인한다.

예시:

- `feature/#12-login`
- `feature/12-login`
- `issue-12-login`
- 사용자가 "12번 이슈 PR 작성해줘"라고 요청한 경우

이슈 번호가 여러 개면 관련 이슈를 모두 확인하고, 실제 변경사항과 직접 연결된 이슈만 PR 본문에 포함한다.

## 이슈 연동 규칙

- GitHub 이슈 번호가 확인되면 PR 본문에 `Closes #이슈번호`를 포함한다.
- `Closes #이슈번호`는 PR이 기본 브랜치에 머지될 때 해당 이슈를 자동으로 닫기 위한 문구다.
- 이슈 번호는 사용자 요청, 브랜치명, 커밋 메시지에서 확인한다.
- 이슈 번호가 확인되지 않으면 임의로 만들지 않고 `확인 필요`로 표시한다.
- 여러 이슈가 직접 관련되어 있으면 각각 별도 줄로 작성한다.

예시:

- Closes #12
- Closes #15

## PR 제목

변경의 핵심 성격에 맞는 태그 하나를 사용한다.

- [feat]: 기능 추가
- [fix]: 버그 수정
- [refactor]: 구조 개선
- [docs]: 문서 수정
- [test]: 테스트 추가 또는 수정
- [chore]: 설정, 빌드, 유지보수

예시:

- [feat] 고객 조회 기능 구현
- [fix] 주문 상태 필터링 오류 수정

## PR 본문 형식

## 작업 내용

- 이번 PR에서 작업한 내용을 간단히 요약합니다.

## 변경 이유

- 이 작업이 필요한 이유나 해결하려는 문제를 작성합니다.

## 주요 변경 사항

- 핵심 변경 내용을 정리합니다.
- 변경된 주요 파일, API, 화면, 로직이 있다면 함께 적습니다.

## 테스트 결과

- [ ] 로컬 실행 확인
- [ ] 단위 테스트 통과
- [ ] API 테스트 확인
- [ ] 화면 동작 확인

테스트 내용:
- 예: 회원가입 API 정상 응답 확인
- 예: 로그인 실패 케이스 확인

## AI 활용 기록

사용한 AI 도구:
- 예: ChatGPT, Claude, Codex, Cursor 등

활용한 부분:
- 예: 코드 초안 작성
- 예: 리팩토링 방향 검토
- 예: 테스트 케이스 아이디어 도출
- 예: 오류 원인 분석

검토 및 수정한 내용:
- 예: 생성된 코드의 로직을 직접 검토하고 프로젝트 구조에 맞게 수정함
- 예: 보안상 민감 정보가 포함되지 않았는지 확인함
- 예: 테스트를 실행해 정상 동작을 확인함

## 관련 Issue

- Closes #

## 체크리스트

- [ ] 하나의 목적만 가진 PR이다.
- [ ] 관련 Issue를 연결했다.
- [ ] 관련 Milestone이 지정되어 있다.
- [ ] GitHub Project에 추가되어 있다.
- [ ] Project Status를 `In Review`로 변경했다.
- [ ] 테스트 또는 동작 확인 내용을 작성했다.
- [ ] AI 활용 기록을 작성했다.
- [ ] 불필요한 디버깅 코드가 없다.
- [ ] 민감 정보가 포함되지 않았다.
- [ ] 리뷰어가 이해하기 어려운 부분에는 설명을 남겼다.

## 참고 사항

- 리뷰어가 알아야 할 내용, 고민한 점, 논의가 필요한 부분을 작성합니다.

## 관련 Issue 작성

- 이슈 번호가 확인되면 `Closes #이슈번호` 형식으로 작성한다.
- 이슈 번호가 여러 개면 이슈마다 한 줄씩 작성한다.
- 이슈 번호가 확인되지 않으면 `확인 필요`로 작성한다.
- 이슈 자동 종료가 필요하지 않은 관련 이슈는 `Related to #이슈번호` 형식을 사용할 수 있다.
- 관련 Milestone, GitHub Project, Project Status는 실제 GitHub 화면에서 지정해야 하므로 PR 본문 체크리스트에 확인 항목으로만 둔다.

## AI 활용 기록 작성

- 구현 과정에서 사용자가 Codex에 요청한 내용을 확인할 수 있으면 1~3개로 요약한다.
- 확인할 수 없으면 확인 불가로 적는다.
- 원문 프롬프트, 민감정보, 세션 ID, 로그 경로는 포함하지 않는다.
- PR 작성 요청이나 단순 상태 확인 요청은 제외한다.
