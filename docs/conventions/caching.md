# Caching

## Status

이 문서는 프로젝트 고도화 단계에서 캐싱이 필요해질 때 작성한다.

현재 단계에서는 캐싱 대상과 저장소가 확정되지 않았으므로 구체적인 구현 규칙을 정하지 않는다.

## 작성 전 확인할 것

- 캐싱이 실제로 필요한 성능 병목인지 확인한다.
- 캐싱 대상을 정한다. 예: 조회가 잦고 변경이 적은 데이터, 외부 API 응답, 집계 결과
- 캐싱하지 말아야 할 대상을 정한다. 예: 사용자별 민감 정보, 자주 변경되는 데이터
- 캐시 저장소를 정한다. 예: 로컬 메모리, Redis
- 캐시 키 네이밍 규칙을 정한다.
- TTL 기준을 정한다.
- 캐시 무효화 전략을 정한다. 예: 수정/삭제 시 evict, 주기적 갱신, write-through
- 캐시 불일치가 발생했을 때 허용 가능한 범위를 정한다.
- 장애 시 동작을 정한다. 예: 캐시 장애 시 DB 조회 fallback
- 테스트 범위를 정한다. 예: 캐시 hit/miss, evict, TTL, 장애 fallback
