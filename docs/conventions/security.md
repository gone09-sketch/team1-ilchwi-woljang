# Security

## 목적

인증과 인가 기준을 일관되게 관리한다.

사용자 인증 상태, 권한, 민감 정보 처리를 명확히 해 보안 실수를 줄인다.

## 기본 원칙

- 인증이 필요한 API와 공개 API를 구분한다.
- 인증은 사용자가 누구인지 확인하는 과정이다.
- 인가는 인증된 사용자가 해당 작업을 할 권한이 있는지 확인하는 과정이다.
- 비밀번호, 토큰, 인증번호 같은 민감 정보는 응답이나 로그에 노출하지 않는다.
- 보안 관련 예외 응답 형식은 `exception.md`, `api-response.md`를 따른다.

## 인증

JWT 기반 stateless 인증을 우선 사용한다.

인증이 필요한 요청은 Authorization 헤더의 Bearer 토큰을 통해 사용자 정보를 확인한다.

예시:

```text
Authorization: Bearer {accessToken}
```

토큰이 없거나, 만료되었거나, 위조된 경우 인증 실패로 처리한다.

인증 실패는 401 Unauthorized로 응답한다.

## 인가

인가가 필요한 기능은 현재 사용자가 해당 리소스에 접근할 수 있는지 확인한다.

예시:

- 본인 프로필만 수정 가능
- 본인 게시글만 삭제 가능
- 관리자만 접근 가능한 API
- 채팅방 참여자만 메시지 조회 가능

권한 부족은 403 Forbidden으로 응답한다.

## Controller에서 인증 사용자 사용

Controller는 Security에서 검증된 사용자 정보를 전달받는다.

Controller는 인증 사용자 전체 객체보다 필요한 식별자 값을 Service에 전달하는 것을 우선한다.

예시:

- `userId`
- `email`
- `role`

구체적인 전달 방식은 프로젝트 구현 방식에 맞춘다.

예시:

- `@AuthenticationPrincipal`
- 커스텀 인증 사용자 어노테이션
- SecurityContext 사용

## Service에서 권한 검증

소유권이나 비즈니스 권한 검증은 Service에서 확인한다.

예시:

- 요청한 사용자가 해당 게시글의 작성자인지
- 요청한 사용자가 채팅방 참여자인지
- 요청한 사용자가 해당 리소스를 수정할 수 있는지

Security 설정만으로 판단하기 어려운 권한은 Service에서 한 번 더 검증한다.

## 비밀번호

비밀번호는 평문으로 저장하지 않는다.

비밀번호는 반드시 단방향 해시로 저장한다.

예시:

- BCrypt

비밀번호 검증은 원문 비밀번호를 복호화하는 방식이 아니라, 입력값과 해시값을 비교하는 방식으로 처리한다.

## 토큰

Access Token과 Refresh Token의 역할을 구분한다.

- Access Token: API 인증에 사용한다.
- Refresh Token: Access Token 재발급에 사용한다.

Refresh Token 저장 위치와 만료 정책은 팀에서 별도로 정한다.

토큰은 로그나 응답에 불필요하게 노출하지 않는다.

## CSRF

Authorization 헤더 기반 stateless JWT 인증을 사용한다면 CSRF 비활성화를 검토할 수 있다.

JWT를 쿠키에 저장하거나 세션 기반 인증을 사용하는 경우 CSRF 보호를 다시 검토한다.

## 피해야 할 Security

- 인증 없이 보호 API에 접근 가능한 구조
- 권한 검증 없이 다른 사용자의 리소스를 수정/삭제할 수 있는 구조
- 비밀번호를 평문으로 저장하는 구조
- 토큰, 인증번호, 비밀번호를 로그에 남기는 구조
- 모든 API를 무분별하게 공개하는 Security 설정
