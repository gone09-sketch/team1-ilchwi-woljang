# 테스트 코드 컨벤션

## 목적

테스트는 많이 작성하는 것보다 핵심 기능을 안정적으로 검증하는 것을 우선한다.

새 기능을 구현할 때 자주 깨지는 테스트보다, 사용자가 기대하는 동작과 중요한 비즈니스 규칙을 검증하는 테스트를 작성한다.

## 테스트 우선순위

아래 우선순위는 기본적으로 현재 브랜치에서 새로 구현하거나 변경한 범위 안에서 판단한다.

다만 인증/인가, 보안 필터, 권한 검증처럼 영향 범위가 넓은 기능을 변경했다면 항상 최우선으로 검토한다.

우선순위는 아래 순서로 판단한다.

1. 현재 브랜치에서 새로 구현하거나 변경한 핵심 기능
2. 실패하면 사용자 흐름이 깨지는 기능
3. 인증/인가처럼 접근 권한이 걸린 기능
4. DB 저장, 수정, 삭제처럼 데이터 상태가 바뀌는 기능
5. 트랜잭션 롤백이 필요한 기능
6. 예외 상황과 실패 응답
7. JPA 연관관계나 조회 성능에 영향을 줄 수 있는 기능

단순 getter/setter, private 메서드, 구현 세부사항, 문구 변경에 민감한 테스트는 우선 작성하지 않는다.

## 테스트 종류 선택

### Controller 테스트

요청 URL, HTTP Method, Request, Response, Status Code를 검증한다.

`@Valid` 같은 요청 형식 검증은 Controller 테스트에서 우선 검증한다.

Service에서 발생한 예외가 `@ControllerAdvice` 또는 `GlobalExceptionHandler`를 통해 어떤 HTTP 응답으로 변환되는지는 Controller 테스트에서 검증한다.

예시:

- 필수 필드 누락
- 형식 오류
- 타입 오류
- 요청 본문 구조 오류
- 인증 실패 응답

### 인증/인가 테스트 기준

Spring Security 테스트는 검증 목적에 따라 범위를 구분한다.

#### 필터 통과 이후 로직을 검증하는 경우

Controller, 요청 검증, 권한 통과 이후의 비즈니스 흐름만 확인하는 테스트에서는 Mock 인증을 사용할 수 있다.

예시:

- `@WithMockUser`
- 테스트용 SecurityContext 설정
- Mock 인증 객체 주입

이 방식은 Security Filter Chain, JWT 필터, 실제 인증 실패 흐름을 검증하지 않는다.

#### Security 설정과 권한을 검증하는 경우

URL별 접근 권한, 인증 필요 여부, 권한 부족 응답을 검증할 때는 Spring Security 필터를 포함해서 테스트한다.

이 경우 아래를 확인한다.

- 인증 없이 접근하면 401 응답이 나는지
- 인증은 되었지만 권한이 부족하면 403 응답이 나는지
- 허용된 권한으로 접근하면 정상 응답이 나는지
- 역할 이름과 권한 이름이 프로젝트 규칙과 일치하는지

`@AutoConfigureMockMvc(addFilters = false)`처럼 필터를 끄는 설정은 Controller 로직만 검증할 때만 사용한다.

#### JWT 필터 자체를 검증하는 경우

토큰 누락, 만료, 위조, 잘못된 서명, 권한 부족을 검증해야 한다면 실제 JWT를 요청 헤더에 넣고 Security Filter Chain을 통과시키는 방식으로 테스트한다.

Security 설정 테스트와 JWT 필터 테스트에서 사용하는 정상 토큰, 만료 토큰, 잘못된 서명 토큰, 특정 권한 토큰은 테스트용 JWT 생성 유틸을 통해 만든다.

이 경우 아래 항목을 확인한다.

- 토큰이 없을 때의 응답
- 만료된 토큰일 때의 응답
- 위조된 토큰일 때의 응답
- 권한이 부족할 때의 응답
- 인증 실패가 공통 에러 응답 형식으로 변환되는지

#### CSRF 기준

JWT 기반 stateless 인증을 사용하고 실제 Security 설정에서 CSRF를 비활성화했다면 테스트도 그 설정을 따른다.

세션 기반 인증이나 form login을 사용하는 경우에는 CSRF 토큰이 필요한 요청을 별도로 검증한다.

### Service 테스트

비즈니스 규칙, 예외 상황, 트랜잭션 흐름을 검증한다.

Service 단위 테스트에서는 Repository, 외부 API, 메일, 파일, 결제 모듈처럼 외부 의존성을 Mock으로 대체할 수 있다.

비즈니스 규칙 위반은 Service 테스트에서 우선 검증한다.

예시:

- 중복 가입 불가
- 재고 부족
- 본인 소유 데이터만 수정 가능
- 주문 상태가 특정 상태일 때만 취소 가능

### Repository 테스트

직접 작성한 쿼리, 조회 조건, 정렬, 페이징, 연관관계를 검증한다.

단순 JpaRepository 기본 메서드는 우선 테스트하지 않는다.

기본 CRUD 단계에서는 Repository 테스트보다 Service 테스트와 Controller 테스트를 우선 작성한다.

Repository 테스트는 복잡한 쿼리, 정렬, 페이징, 연관관계, DB 제약조건처럼 실제 DB 동작 확인이 필요한 경우에 작성한다.

### 통합 테스트

여러 계층이 함께 동작해야 의미가 있는 핵심 흐름을 검증한다.

통합 테스트는 기본적으로 `@SpringBootTest` 기반으로 작성한다.

DB 검증이 필요한 경우 프로젝트 초반에는 H2 또는 로컬 테스트 DB를 임시로 사용할 수 있고, Docker 환경이 준비되면 Testcontainers MySQL 도입을 검토한다.

외부 API, 메일, 결제, 파일 저장소 같은 외부 시스템은 실제 서비스를 호출하지 않고 Mock, Fake, Stub으로 대체한다.

비용이 크므로 핵심 사용자 흐름에만 우선 적용한다.

## 테스트 네이밍

테스트 메서드명은 영어로 작성하고, `@DisplayName`은 한글로 작성한다.

이 규칙은 Controller, Service, Repository, 통합 테스트에 동일하게 적용한다.

메서드명은 아래 형식을 권장한다.

given_조건_when_상황_then_결과

예시:

void givenDuplicateEmail_whenSignUp_thenThrowException()

`@DisplayName`은 테스트 의도를 사람이 읽기 쉽게 작성한다.

예시:

@DisplayName("이미 가입된 이메일이면 회원가입에 실패한다")

한글 메서드명은 사용하지 않는다.

이유:

- Java에서는 한글 메서드명도 가능하지만, IDE, 빌드 도구, 협업 환경에서 일관성이 떨어질 수 있다.
- 대신 `@DisplayName`을 한글로 작성하면 테스트 의도를 충분히 드러낼 수 있다.

## 테스트 작성 기준

- 테스트 이름은 무엇을 검증하는지 드러나게 작성한다.
- 하나의 테스트는 하나의 핵심 상황만 검증한다.
- 내부 구현 방식보다 외부에서 확인 가능한 결과를 검증한다.
- 테스트가 실패했을 때 원인을 추적할 수 있어야 한다.
- 테스트를 통과시키기 위해 핵심 검증을 약하게 만들지 않는다.
- 테스트를 위해 프로덕션 코드를 임의로 수정하지 않는다.

## 트랜잭션 롤백 테스트

트랜잭션 롤백을 검증하는 테스트는 테스트 자체의 자동 롤백과 프로덕션 코드의 롤백을 구분한다.

Spring Boot 테스트에서 테스트 메서드에 `@Transactional`을 붙이면 테스트 종료 후 DB 변경사항이 자동으로 롤백될 수 있다.

따라서 프로덕션 코드의 롤백 동작을 검증할 때는 테스트 메서드에 `@Transactional`을 붙이지 않는 것을 우선 검토한다.

테스트 메서드에 `@Transactional`을 붙이지 않는 경우, 테스트 종료 후 DB에 남은 데이터는 `@AfterEach`, cleanup 유틸, 또는 테스트 격리 전략으로 직접 정리한다.

이 정리를 하지 않으면 다른 테스트가 이전 테스트의 데이터에 영향을 받을 수 있다.

롤백 테스트에서는 아래를 확인한다.

- 예외 발생 후 DB에 데이터가 남지 않는지
- 일부 데이터만 저장되는 상태가 생기지 않는지
- 서비스 메서드의 `@Transactional` 범위가 의도대로 동작하는지
- 예외를 잡아먹어서 rollback이 되지 않는 구조는 아닌지

DB 상태를 확인할 때는 영속성 컨텍스트 캐시가 아니라 실제 DB 상태를 확인해야 한다.

필요한 경우 `flush`, `clear` 또는 별도 조회를 통해 실제 DB 상태를 다시 확인한다.

## 테스트 데이터

테스트 데이터는 테스트에서 사용하는 더미 객체, 요청 DTO, Entity, DB 저장 데이터, 토큰, 날짜 값을 의미한다.

테스트 데이터는 각 테스트가 필요한 만큼 직접 생성하는 것을 우선한다.

여러 테스트가 같은 변경 가능한 데이터를 공유하지 않는다.

`@BeforeEach`는 모든 테스트에 공통으로 필요한 설정이나 Mock 초기화에만 사용하고, 테스트별 의미가 있는 데이터는 각 테스트 안에서 만든다.

반복되는 생성 코드가 많아지면 Fixture 또는 Builder를 사용할 수 있다.

시간, 랜덤값, 외부 API처럼 결과가 흔들리는 요소는 가능한 한 통제한다.

## DB 테스트 환경

프로젝트 초반에는 Docker와 Testcontainers를 필수로 사용하지 않는다.

현재 단계에서는 필요한 Repository 테스트에 H2 또는 로컬 테스트 DB를 사용할 수 있다.

단, H2는 MySQL과 문법, 타입, 제약조건, dialect 동작이 다를 수 있으므로 MySQL 동작과 완전히 같다고 가정하지 않는다.

중요한 Repository 테스트는 Docker 환경이 준비된 이후 Testcontainers MySQL로 보완한다.

Docker와 배포 준비 단계에서는 Testcontainers MySQL 도입을 우선 검토한다.

이 단계에서 Testcontainers MySQL을 우선 적용할 대상은 아래와 같다.

- Repository 쿼리 검증
- Entity 매핑 검증
- unique, nullable, enum, relation 같은 DB 제약조건 검증
- MySQL 문법이나 dialect 영향을 받는 쿼리 검증
- H2 또는 로컬 테스트 DB와 실제 MySQL의 차이로 오류가 날 수 있는 기능 검증

## 피해야 할 테스트

- 단순 getter/setter 테스트
- 의미 없는 CRUD 반복 테스트
- private 메서드 직접 테스트
- Mock 호출 횟수에만 의존하는 테스트
- 문구 하나만 바뀌어도 깨지는 테스트
- 구현 구조가 조금 바뀌면 바로 깨지는 테스트
