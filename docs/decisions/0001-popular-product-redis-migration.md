# [의사결정] 다중 WAS 환경 대응을 위한 Redis 글로벌 캐시 도입 및 Record 역직렬화 트러블슈팅

- 번호: 0001
- 작성일: 2026-07-01
- 상태: 결정됨
- 관련 기능/도메인: 인기 상품 조회 최적화, 캐싱 전략

## 배경 / 문제
- 메인 화면에 위치한 인기 상품 조회 API의 병목 현상을 방지하기 위해 로컬 캐시(Caffeine)를 최초 검토하고 적용했음.
- 그러나 실무 사양처럼 서비스를 다중 WAS 환경(Scale-out)으로 구성하여 로컬 포트 `8080`과 `8081`에 각각 다른 애플리케이션 인스턴스를 띄워 테스트해 본 결과, 하나의 인스턴스에서 데이터가 변경되었을 때 다른 WAS 인스턴스의 로컬 캐시가 즉시 갱신되지 않아 **동일한 요청에 대해 각 WAS가 다른 캐시 데이터를 반환하는 정합성 불일치 문제**가 발생함.
- 따라서 다중 WAS 상태에서도 항상 동일한 캐시 데이터를 보장할 수 있는 새로운 분산 캐싱 아키텍처 도입 결정이 필요했음.
- 캐시 전환 도중 Java의 `record` 타입으로 설계된 `PopularProductResponse` 클래스가 JSON 역직렬화 시 `ClassCastException`을 발생시키는 기술적 장애를 겪었음.

## 고려한 선택지

### 선택지 A: Caffeine 로컬 캐시 + 캐시 동기화 메커니즘
로컬 메모리(Caffeine)를 그대로 사용하되, 한 WAS에서 데이터 변경 이벤트가 발생하면 MQ나 Webhook 등을 이용해 다른 WAS에게 "로컬 캐시를 비우라"고 알리는 방식.
- **장점**: 인메모리 조회 속도가 극도로 빠름 (네트워크 I/O가 아예 없음).
- **단점**: WAS 인스턴스가 늘어날수록 전파 과정의 오버헤드가 크고 신뢰성이 떨어짐. 캐시 비우기 동기화 로직 구현 및 관리 오버헤드가 큼.

### 선택지 B: Redis 기반의 글로벌 공유 캐시 (채택)
분산 외부 캐시 저장소인 Redis를 WAS 외부에 띄우고, 모든 WAS 인스턴스가 단 하나의 글로벌 Redis 캐시를 공유하는 방식.
- **장점**:
  - 다중 WAS 환경에서도 100% 동일한 캐시 데이터(정합성)가 완벽히 보장됨.
  - 별도의 노드 간 동기화 이벤트 처리가 필요 없어 코드가 단순하고 확장성이 높음.
- **단점**:
  - 외부 Redis와 TCP 통신을 거쳐야 하므로 네트워크 I/O 비용이 발생하여 로컬 캐시 대비 조회가 미세하게 느림.
  - Redis 단일 장애점(SPOF)이 될 위험성이 존재하여 고가용성(HA) 구성 등의 관리가 필요함.

## 결정

**선택지 B: Redis 기반의 글로벌 공유 캐시**를 선택하고, Jackson 직렬화기 튜닝을 통해 Java `record` 직렬화 문제를 해결하여 최종 적용한다.

## 결정 이유

- **완벽한 정합성 보장**: 대규모 트래픽 환경이나 오토스케일링으로 동적 WAS 인스턴스가 추가되어도, 모든 인스턴스가 동일한 Redis를 바라보아 데이터 왜곡 없는 완전한 정합성을 달성함.
- **아키텍처의 단순화**: 노드 간의 복잡한 로컬 캐시 무효화 전파 메커니즘 없이, 하나의 캐시 TTL 만료와 캐시 웜업 주기 제어로 전체 노드의 정합성이 단순하고 깨끗하게 유지됨.

## 감수한 것 (트레이드오프)

- 로컬 캐싱 대비 네트워크 I/O 비용 추가 발생.
- **클래스 메타정보 의존성**:
  - `GenericJackson2JsonRedisSerializer`를 사용할 때 `record` 역직렬화 문제를 해결하기 위해, 캐시 전용 `ObjectMapper`를 구성하여 `ParameterNamesModule`과 `JavaTimeModule`을 직접 등록해 주었음.
  - 이를 통해 `record` 스펙을 그대로 유지하고 Redis 내부 데이터를 **예쁜 JSON 형태로 눈에 보이게 확인**할 수 있도록 구현했음.
  - 다만, JSON 데이터 내에 다형성을 구분하기 위해 클래스 메타정보(`@class` 속성)가 포함되므로, 추후 리팩토링 등으로 클래스 경로가 변경되면 기존 Redis 캐시를 전체 플러시(Flush)해야 하는 관리 오버헤드가 단점으로 남음.

## 결과 / 후속

- 두 개의 로컬 포트(`8080`, `8081`)로 동시에 WAS를 구동하여 데이터 조작 실험 진행:
  - 캐시가 적재된 뒤 두 WAS에 동일 조회를 날렸을 때 **100% 일치하는 캐시 데이터를 반환함**을 확인.
  - Redis 내부의 캐시 값이 외계어 바이트 코드가 아닌 **정상적인 가독형 JSON 문자열**로 완벽하게 기록되는 것을 개발자 툴로 확인 완료.
  - 백그라운드 웜업 스케줄러(`PopularProductCacheScheduler`)를 통해 Redis 캐시를 만료 전 갱신하도록 후속 조치함 (단, 테스트 환경 오염 방지를 위해 테스트 프로필에서는 스케줄러가 차단되도록 `@Profile("!test")` 적용).
