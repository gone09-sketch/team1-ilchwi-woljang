# Git & GitHub 컨벤션

## 1. 기본 원칙

이 프로젝트는 GitHub Issue, Milestone, Pull Request를 기준으로 작업을 관리합니다.

기본 작업 흐름은 아래 순서를 따릅니다.

1. GitHub Milestone 생성
2. Milestone에 포함될 Issue 생성
3. Issue 번호 기준으로 브랜치 생성
4. 작업 단위별 커밋 작성
5. Pull Request 생성
6. 코드 리뷰
7. Squash Merge
8. Issue 종료 및 Milestone 진행률 확인

GitHub Milestone은 일정 관리 단위로 사용합니다.

Issue는 실제 작업 단위입니다.

Pull Request는 코드 변경 검토 단위입니다.

---

## 2. Milestone 컨벤션

Milestone은 특정 기간 또는 특정 배포 목표를 관리하기 위해 사용합니다.

Milestone은 너무 작게 만들지 않고, 여러 Issue를 묶을 수 있는 단위로 생성합니다.

추천 형식은 아래와 같습니다.

`버전 또는 기간 - 목표`

예시:

- `v1.0.0 - MVP`
- `v1.1.0 - 결제/환불 기능`
- `2026-07-W1 - 회원/인증 기능`
- `2026-07-W2 - 주문/결제 기능`

Milestone에는 반드시 Due date를 설정합니다.

Due date는 해당 Milestone의 목표 완료일입니다.

예시:

| Milestone | Due date | 목적 |
| --- | --- | --- |
| `v1.0.0 - MVP` | 2026-07-10 | 핵심 기능 1차 완성 |
| `v1.1.0 - 결제/환불 기능` | 2026-07-20 | 결제 및 환불 기능 추가 |
| `2026-07-W1 - 회원/인증 기능` | 2026-07-05 | 회원가입, 로그인 구현 |

## 3. Milestone 사용 규칙

모든 작업 Issue는 가능한 한 하나의 Milestone에 연결합니다.

Milestone은 일정 관리 기준이므로 아래 기준으로 사용합니다.

- 이번 일정에 반드시 끝내야 하는 작업만 포함합니다.
- 아직 범위가 확정되지 않은 작업은 Milestone에 바로 넣지 않습니다.
- 일정이 밀리면 Issue를 다음 Milestone으로 이동할 수 있습니다.
- 완료되지 않은 Issue가 남아 있으면 Milestone을 닫지 않습니다.

Milestone에 넣기 좋은 Issue 예시:

- `[feat] 로그인 API 구현`
- `[fix] 결제 상태 검증 오류 수정`
- `[docs] 환불 API 문서 작성`

Milestone에 넣기 애매한 Issue 예시:

- `[idea] 나중에 관리자 기능 개선`
- `[research] 배포 방법 조사`
- `[todo] 언젠가 성능 개선`

이유:

- Milestone은 실제 일정 관리 도구입니다.
- 범위가 불명확한 작업을 넣으면 진행률과 일정 판단이 어려워집니다.

## 4. Issue 컨벤션

Issue는 실제 작업 단위입니다.

Issue 제목은 아래 형식을 사용합니다.

`[타입] 작업 내용`

예시:

- `[feat] 로그인 API 구현`
- `[fix] 주문 상태 필터링 오류 수정`
- `[refactor] 결제 서비스 책임 분리`
- `[docs] 환불 API 문서 추가`
- `[test] 회원 가입 서비스 테스트 추가`

Issue 본문은 아래 형식을 사용합니다.

-

### 작업 내용

-

### 완료 조건

- [ ]

### 연결 Milestone

-

### 참고 사항

-

Issue는 생성 후 적절한 Milestone에 연결합니다.

Issue가 PR로 해결되는 경우 PR 본문에 `Closes #이슈번호`를 작성합니다.

## 5. Label 컨벤션

Label은 Issue와 PR의 성격과 상태를 구분하기 위해 사용합니다.

Milestone이 일정 관리 기준이라면, Label은 작업의 종류와 상태를 나타냅니다.

추천 Label은 아래와 같습니다.

| Label | 의미 |
| --- | --- |
| `type: feature` | 기능 추가 |
| `type: bug` | 버그 수정 |
| `type: refactor` | 리팩토링 |
| `type: docs` | 문서 수정 |
| `type: test` | 테스트 |
| `type: chore` | 설정, 빌드, 유지보수 |
| `status: todo` | 작업 전 |
| `status: in-progress` | 작업 중 |
| `status: review` | 리뷰 중 |
| `status: done` | 완료 |
| `priority: high` | 높은 우선순위 |
| `priority: medium` | 보통 우선순위 |
| `priority: low` | 낮은 우선순위 |

처음부터 Label을 너무 많이 만들지 않습니다.

기본적으로 `type`, `status`, `priority` 정도만 사용합니다.

## 6. Branch 컨벤션

브랜치는 Issue 번호를 기준으로 생성합니다.

형식은 아래와 같습니다.

`타입/이슈번호-작업요약`

예시:

- `feat/12-login-api`
- `fix/18-payment-status-error`
- `refactor/21-order-service`
- `docs/25-refund-api-docs`
- `test/30-member-service-test`
- `chore/33-gradle-setting`

브랜치 타입은 아래 기준을 따릅니다.

| 타입 | 의미 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `docs` | 문서 수정 |
| `test` | 테스트 추가 또는 수정 |
| `chore` | 설정, 빌드, 의존성, 유지보수 |

브랜치명에는 `#`을 넣지 않습니다.

좋은 예:

- `feat/12-login-api`

피하는 예:

- `feature/#12-login`

이유:

- `#` 문자는 터미널, URL, 일부 도구에서 혼동될 수 있습니다.
- 이슈 번호는 숫자만 사용해도 충분히 추적 가능합니다.

## 7. 메인 브랜치 전략

기본 브랜치는 아래 구조를 사용합니다.

| 브랜치 | 역할 |
| --- | --- |
| `main` | 실제 배포 가능한 안정 브랜치 |
| `develop` | 다음 배포를 준비하는 통합 브랜치 |
| `feat/*` | 기능 개발 브랜치 |
| `fix/*` | 버그 수정 브랜치 |
| `refactor/*` | 리팩토링 브랜치 |
| `docs/*` | 문서 수정 브랜치 |
| `test/*` | 테스트 작업 브랜치 |
| `chore/*` | 설정, 빌드, 유지보수 브랜치 |

개인 프로젝트나 학습용 프로젝트에서는 `main` + 작업 브랜치만 사용해도 됩니다.

팀 프로젝트 또는 포트폴리오 프로젝트에서는 `main`, `develop`, 작업 브랜치 구조를 권장합니다.

## 8. Commit 메시지 컨벤션

커밋 메시지는 아래 형식을 사용합니다.

`type: 변경 내용 요약`

예시:

- `feat: 로그인 API 구현`
- `fix: 결제 상태 검증 오류 수정`
- `refactor: 주문 생성 로직을 서비스 계층으로 분리`
- `docs: 환불 API 명세 추가`
- `test: 회원 가입 서비스 테스트 추가`
- `chore: Gradle 의존성 정리`

필요하면 scope를 사용할 수 있습니다.

`type(scope): 변경 내용 요약`

예시:

- `feat(auth): 로그인 API 구현`
- `fix(payment): 결제 상태 검증 오류 수정`
- `refactor(order): 주문 생성 책임 분리`

scope는 영향을 받은 도메인이나 모듈을 의미합니다.

예시:

- `auth`
- `member`
- `order`
- `payment`
- `admin`

커밋은 가능한 한 하나의 의도만 담습니다.

좋은 예:

- `feat: 환불 요청 API 구현`
- `test: 환불 요청 서비스 테스트 추가`
- `docs: 환불 API 문서 추가`

피하는 예:

- `feat: 환불 기능 구현하고 테스트 추가하고 문서 수정`

이유:

- 하나의 커밋에 여러 변경이 섞이면 문제 원인을 추적하기 어렵습니다.
- 커밋 단위가 작을수록 리뷰와 롤백이 쉬워집니다.

## 9. PR 제목 컨벤션

PR 제목은 아래 형식을 사용합니다.

`[타입] 작업 내용`

예시:

- `[feat] 로그인 API 구현`
- `[fix] 주문 상태 필터링 오류 수정`
- `[refactor] 결제 서비스 책임 분리`
- `[docs] 환불 API 문서 추가`
- `[test] 회원 가입 서비스 테스트 추가`
- `[chore] Gradle 의존성 정리`

PR 제목은 변경의 핵심이 한눈에 보이도록 작성합니다.

좋은 예:

- `[feat] 환불 요청 API 구현`
- `[fix] 주문 상태 필터링 조건 오류 수정`

피하는 예:

- `[feat] 기능 구현`
- `[fix] 버그 수정`

## 10. PR 본문 컨벤션

PR 본문 형식은 아래 템플릿 파일을 단일 기준으로 사용합니다.

→ [`.github/PULL_REQUEST_TEMPLATE.md`](../.github/PULL_REQUEST_TEMPLATE.md)

PR은 실제 변경 파일과 diff에 근거해서만 작성합니다.

구현되지 않은 내용, 향후 계획, 추측은 포함하지 않습니다.

확인하지 않은 테스트는 완료로 표시하지 않습니다.

## 11. 연결 이슈 작성 규칙

이슈 번호가 확인되면 아래 형식을 사용합니다.

- `Closes #12`

`Closes #12`는 PR이 기본 브랜치에 머지될 때 GitHub Issue #12를 자동으로 닫기 위한 문구입니다.

여러 이슈가 직접 관련되어 있으면 각각 별도 줄로 작성합니다.

예시:

- `Closes #12`
- `Closes #15`

자동 종료가 필요하지 않은 관련 이슈는 아래 형식을 사용합니다.

- `Related to #12`

이슈 번호가 확인되지 않으면 임의로 만들지 않고 아래처럼 작성합니다.

- `확인 필요`

## 12. 테스트 및 확인 작성 규칙

테스트 및 확인 항목은 실제로 수행한 것만 체크합니다.

예시:

- [ ] 단위 테스트 실행
- [ ] 통합 테스트 실행
- [ ] IntelliJ에서 애플리케이션 실행 확인
- [ ] Postman 또는 Swagger로 API 수동 확인
- [ ] 테스트 미실행

테스트를 실행하지 않았다면 완료한 것처럼 표시하지 않습니다.

좋은 예:

- [x] IntelliJ에서 애플리케이션 실행 확인
- [x] Postman으로 로그인 API 정상 응답 확인
- [ ] 통합 테스트 미실행

피하는 예:

- [x] 테스트 완료

이유:

- 어떤 테스트를 했는지 알 수 없습니다.
- 리뷰어가 검증 범위를 판단하기 어렵습니다.

## 13. AI 활용 기록 작성 규칙

AI를 활용한 경우, 구현 과정에서 도움받은 내용을 1~3개로 요약합니다.

예시:

- 변경 파일과 diff를 기준으로 PR 요약을 정리하는 데 Codex를 활용했습니다.
- 예외 처리 방식 검토에 Codex를 활용했습니다.
- 테스트 케이스 작성 방향을 검토하는 데 Codex를 활용했습니다.

포함하지 않는 내용:

- 원문 프롬프트
- 민감정보
- 세션 ID
- 로그 경로
- 단순 상태 확인 요청
- PR 작성 요청 자체

확인할 수 없는 경우 아래처럼 작성합니다.

- 확인 불가

## 14. 코드 리뷰 기준

코드 리뷰는 아래 항목을 기준으로 진행합니다.

### 가독성

- 변수명과 메서드명이 역할을 명확히 표현하는가?
- 메서드가 너무 많은 책임을 가지고 있지 않은가?
- 중복 코드가 과도하지 않은가?

### 설계

- Controller, Service, Repository의 책임이 분리되어 있는가?
- 비즈니스 로직이 Controller에 과도하게 들어가 있지 않은가?
- DTO와 Entity의 역할이 구분되어 있는가?

### 확장성

- 추후 기능 추가 시 기존 코드를 과도하게 수정하지 않아도 되는가?
- 조건문이 너무 복잡하게 늘어나고 있지 않은가?
- 도메인 규칙이 한 곳에 모여 있는가?

### 성능

- 불필요한 쿼리가 발생하지 않는가?
- JPA 사용 시 N+1 문제가 발생하지 않는가?
- 반복문 안에서 DB 조회가 발생하지 않는가?

### 예외 처리

- 실패 상황을 적절히 처리하는가?
- 사용자에게 필요한 에러 메시지를 제공하는가?
- 예외가 무시되거나 숨겨지지 않는가?

### 실무 스타일

- 프로젝트 컨벤션을 지키고 있는가?
- 트랜잭션 범위가 적절한가?
- 테스트 가능한 구조인가?
- 유지보수하기 쉬운 코드인가?

리뷰 코멘트는 단순 지적만 하지 않고, 문제 이유와 개선 방향을 함께 작성합니다.

예시:

현재 Controller에서 결제 검증 로직을 직접 처리하고 있습니다.

이 로직은 비즈니스 규칙에 가깝기 때문에 Service 계층으로 이동하는 것이 좋습니다.

그래야 나중에 관리자 결제 승인 기능이 추가되어도 같은 검증 로직을 재사용할 수 있습니다.

## 15. 머지 전략

기본 머지 방식은 Squash Merge를 사용합니다.

Squash Merge는 PR 안의 여러 커밋을 하나의 커밋으로 합쳐서 머지하는 방식입니다.

장점:

- `main`, `develop` 브랜치 히스토리가 깔끔해집니다.
- PR 단위로 변경 이력을 추적하기 쉽습니다.
- 학습용 프로젝트와 팀 프로젝트 모두에서 관리하기 쉽습니다.

Squash Merge 커밋 메시지 예시:

- `[feat] 환불 요청 API 구현 (#12)`

커밋 하나하나의 히스토리를 모두 보존해야 하는 경우에는 Merge Commit을 사용할 수 있습니다.

하지만 기본적으로는 Squash Merge를 우선 사용합니다.

## 16. 브랜치 보호 규칙

GitHub Repository Settings에서 아래 규칙을 권장합니다.

- `main` 브랜치 직접 push 금지
- `develop` 브랜치 직접 push 금지
- PR 리뷰 승인 후 머지
- 테스트 실패 시 머지 금지
- 머지 후 작업 브랜치 삭제

이유:

- 리뷰 없이 운영 코드가 변경되는 것을 방지할 수 있습니다.
- 테스트 실패 코드가 메인 브랜치에 들어가는 것을 막을 수 있습니다.
- 브랜치가 계속 쌓여 관리가 어려워지는 문제를 줄일 수 있습니다.

## 17. 권장 작업 흐름

새 작업을 시작할 때는 아래 순서를 따릅니다.

1. GitHub Milestone을 확인합니다.
2. 현재 Milestone에 필요한 Issue를 생성합니다.
3. Issue에 Milestone과 Label을 지정합니다.
4. Issue 번호를 기준으로 브랜치를 생성합니다.
5. 작업을 진행합니다.
6. 의미 있는 단위로 커밋합니다.
7. 원격 저장소에 push합니다.
8. PR을 생성합니다.
9. PR 본문에 작업 내용, 변경 이유, 연결 이슈, 연결 Milestone, 테스트 여부를 작성합니다.
10. 코드 리뷰를 받습니다.
11. 필요한 수정 사항을 반영합니다.
12. Squash Merge합니다.
13. Issue가 자동 종료되었는지 확인합니다.
14. Milestone 진행률을 확인합니다.
15. 머지 후 작업 브랜치를 삭제합니다.

예시 흐름:

- Milestone 생성: `v1.0.0 - MVP`
- Issue 생성: `[feat] 로그인 API 구현`
- Issue Milestone 지정: `v1.0.0 - MVP`
- Branch 생성: `feat/12-login-api`
- Commit 작성: `feat: 로그인 API 구현`
- PR 제목: `[feat] 로그인 API 구현`
- PR 연결 이슈: `Closes #12`
- PR 연결 Milestone: `v1.0.0 - MVP`
- Merge 방식: Squash Merge
